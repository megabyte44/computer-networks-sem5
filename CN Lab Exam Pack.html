Basics

NS2 basics: the skeleton every script follows

Every NS2 script is the same nine steps in the same order; only the topology and the traffic change. NS2 is a discrete-event simulator: you describe a network and a timetable of events in a Tcl script, run ns script.tcl, and it writes a trace file (.tr, one line per packet event) and an animation file (.nam).

The nine steps
  1. Create the simulator.
  2. Open the trace file and the nam file.
  3. Create the nodes.
  4. Create the links between nodes.
  5. Create agents (the transport protocol), attach them to nodes and connect sender to receiver.
  6. Create applications (the traffic source) and attach them to agents.
  7. Schedule events with $ns at time "command".
  8. Write the finish procedure: flush the trace, close the files, start nam, exit.
  9. Call $ns run.

The smallest complete example (a UDP flow from n0 to n2 through n1):

tcl
set ns [new Simulator]

set tf [open out.tr w]
$ns trace-all $tf
set nf [open out.nam w]
$ns namtrace-all $nf

set n0 [$ns node]
set n1 [$ns node]
set n2 [$ns node]

$ns duplex-link $n0 $n1 1Mb 10ms DropTail
$ns duplex-link $n1 $n2 1Mb 10ms DropTail

set udp [new Agent/UDP]
set null [new Agent/Null]
$ns attach-agent $n0 $udp
$ns attach-agent $n2 $null
$ns connect $udp $null

set cbr [new Application/Traffic/CBR]
$cbr attach-agent $udp

$ns at 1.0 "$cbr start"
$ns at 4.0 "$cbr stop"
$ns at 5.0 "finish"

proc finish {} {
    global ns tf nf
    $ns flush-trace
    close $tf
    close $nf
    exec nam out.nam &
    exit 0
}

$ns run

If you can reproduce this from memory, you already have 60 percent of every program. Each later program adds a different protocol, topology or routing command on top of it.

Tcl rules that cause most exam errors
  • set x 5 assigns, $x reads, [cmd] runs a command and returns its result, expr does arithmetic.
  • Inside a proc, outer variables are invisible. Declare them with global, and get the simulator with set ns [Simulator instance] if it is not declared global.
  • The opening brace of a proc must be on the same line as proc. proc finish {} followed by { on the next line is a syntax error.
  • Arrays are written n($i); loops are for {set i 0} {$i < 6} {incr i} { ... }.
  • Commands scheduled with $ns at are strings, so they sit inside double quotes.

Trace file and the awk template

Every analysis script in this pack is the same awk program with one number changed: the node that receives the data. Learn the trace line once and you can read all of them.

A wired trace line (one packet event per line):

text
r 1.025 1 4 cbr 1000 ------- 1 0.0 3.0 5 12
ColumnFieldMeaning
$1event+ enqueued, - dequeued, r received, d dropped
$2timeSimulation time in seconds
$3from nodeNode the packet left
$4to nodeNode the packet is arriving at
$5typetcp, ack, cbr, udp and so on
$6sizePacket size in bytes
$8flow idWhich flow the packet belongs to
$11seqSequence number
$12packet idUnique id

A packet crossing three links produces three r lines, one per hop. Filtering on $4 == SINK_NODE counts it only once, at its last hop. ACKs travel back towards the sender, so they have a different $4 and are not counted.

The awk template
awk
BEGIN { bytes = 0; first = 0; last = 0; flag = 0 }
{
    if ($1 == "r" && $4 == SINK_NODE) {
        bytes += $6
        if (flag == 0) { first = $2; flag = 1 }
        last = $2
    }
}
END {
    t = last - first
    print "Bytes received =", bytes
    print "Time          =", t
    print "Throughput    =", bytes / t, "bytes/sec"
}

Throughput = total bytes received divided by the time between the first and last receive. Multiply by 8 for bits per second.

Wireless traces look different. A wireless trace line has the event first (s send, r receive, D drop), then time, then the node as _3_, then the layer (AGT application, RTR routing, MAC), and the packet type and size further along. That is why the wireless awk script in Program 5 matches on $4 == "AGT" instead of a node number. Program 11 does not need awk: it records throughput inside the simulation with a LossMonitor and a record procedure.

The record procedure, used in 6A, 6B, 7 and 11. It is an alternative to awk: every 0.1 s it reads bytes_ from the sink, writes time value to a file, resets bytes_ to 0 and schedules itself again. xgraph then plots that file. The line bw/time*8/1000000 converts bytes per interval to Mbps.

Unique lines to memorise: new ServerSocket(7777), ss.accept(), new Socket("localhost", 7777), getInputStream() / getOutputStream(), and the pair writeUTF / readUTF.

Aim

To write a client and a server in Java that chat over a TCP connection from two terminals, taking turns, until the client types "over".

Theory
  • A socket is one end of a network connection, identified by an IP address and a port number.
  • TCP is connection oriented: the server waits, the client connects, and then both sides exchange data over reliable byte streams.
  • The server uses ServerSocket(port) to listen. Its accept() call blocks until a client connects and then returns an ordinary Socket for that client.
  • The client uses Socket(host, port) to connect. localhost means the same machine.
  • Each side gets an input stream and an output stream from its Socket. DataOutputStream.writeUTF sends a string and DataInputStream.readUTF reads it back.

The Java socket skeleton (the same shape appears again in Programs 2 and 3)

  1. Server: create ServerSocket, call accept(), wrap the socket's streams, loop reading and writing, close.
  2. Client: create Socket, wrap the streams, loop writing and reading, close.
  3. The server must be running first, and both sides must use the same port.
Procedure
  1. Write Server.java and Client.java in one folder.
  2. Compile: javac Server.java Client.java.
  3. Terminal 1: java Server. It prints "Waiting for Connection.....".
  4. Terminal 2: java Client.
  5. Type a message in the client, press Enter, then type the server's reply in the server terminal. Repeat.
  6. Type over in the client to end the chat.
Code: Server.java
java
import java.net.*;
import java.io.*;

public class Server {
    public static void main(String args[]) throws Exception {

        ServerSocket ss = new ServerSocket(7777);
        System.out.println("Server Started");
        System.out.println("Waiting for Connection.....");

        Socket s = ss.accept();
        System.out.println("Connecton established with Client...");

        DataInputStream dat = new DataInputStream(System.in);
        DataInputStream dis = new DataInputStream(s.getInputStream());
        DataOutputStream dos = new DataOutputStream(s.getOutputStream());

        String clientMessage = " ";
        String my_reply = " ";

        while (!(clientMessage.equalsIgnoreCase("over"))) {
            clientMessage = dis.readUTF();
            System.out.println("Client:" + clientMessage);
            System.out.println("Message:");
            my_reply = dat.readLine();
            dos.writeUTF(my_reply);
        }
    }
}
Code: Client.java
java
import java.net.*;
import java.io.*;

public class Client {
    public static void main(String args[]) throws Exception {

        Socket s = new Socket("localhost", 7777);

        DataInputStream dis = new DataInputStream(System.in);
        DataOutputStream dos = new DataOutputStream(s.getOutputStream());

        String l = " ";
        DataInputStream d = new DataInputStream(s.getInputStream());
        String re = " ";

        while (!(l.equalsIgnoreCase("over"))) {
            System.out.println("Message:");
            l = dis.readLine();
            dos.writeUTF(l);
            re = d.readUTF();
            System.out.println("Server:" + re);
        }

        s.close();
        dos.close();
        d.close();
    }
}
Line-by-line explanation
  • ServerSocket ss = new ServerSocket(7777) opens port 7777 and starts listening. ss.accept() then pauses the server until a client connects.
  • On the server, dat reads the keyboard (System.in), dis reads what the client sent, and dos writes to the client. The client has the same three streams: dis is its keyboard, d is the input from the server, and dos is the output to the server.
  • The loop condition !(clientMessage.equalsIgnoreCase("over")) stops the chat when the client sends "over" in any letter case.
  • The chat is strictly turn based. The client sends first and then waits for a reply, and the server reads, then prompts for its reply, then waits for the next message. Neither side can send twice in a row.
  • After the client sends "over", the server still asks for one last reply, and the client prints it before it exits.
  • readLine() on a DataInputStream is deprecated, so the compiler prints "uses or overrides a deprecated API". It is only a note; the program still compiles and runs.

Viva questions
  • What is a socket? One endpoint of a two-way connection, identified by an IP address and a port.
  • What does accept() do? It blocks until a client connects and returns a new Socket for that client.
  • ServerSocket versus Socket? ServerSocket only listens for connections. Socket carries the actual data.
  • Why TCP and not UDP for a chat? TCP gives a reliable, ordered stream with a connection. UDP is connectionless.
  • Why must the server start first? The client connects to a port that the server must already be listening on; otherwise it gets "Connection refused".
  • What does writeUTF do? It writes a string in a length-prefixed UTF-8 form that readUTF on the other side can read back exactly.
Common errors
  • java.net.ConnectException: Connection refused: the client started before the server, or the port numbers differ.
  • java.net.BindException: Address already in use: an earlier server is still running on port 7777.
  • Class name and file name must match: Server in Server.java.
  • One side typing twice: the chat is turn based, so wait for the other side's prompt.

Unique lines to memorise: the cipher itself, (char)(ch + 3) to encrypt and (char)(ch - 3) to decrypt in 2A, and (c + 3) % 256 and (c - 3 + 256) % 256 in 2B.

Aim

To transfer files between a client and a server over TCP in Java, encrypting the data with a Caesar cipher (shift of 3) before it is sent and decrypting it on arrival.

Theory
  • A Caesar cipher shifts every character by a fixed key. With key 3, 1 becomes 4 and a becomes d. Decryption shifts back by 3.
  • On raw bytes the shift wraps around modulo 256 so the result stays a valid byte: encrypt (c + 3) % 256, decrypt (c - 3 + 256) % 256. The + 256 stops a negative number appearing before the modulo.
  • It is a symmetric cipher: sender and receiver use the same key. It is easy to break (only 255 possible keys, and letter frequencies give it away), so it is a teaching example, not real security.
  • A threaded server gives each connected client its own thread, so several clients can be served at once.

Code: ServerTCP.java
java
import java.io.*;
import java.net.*;

class ServerTCP {
    public static void main(String args[]) throws Exception {
        ServerSocket ss = new ServerSocket(7777);
        System.out.println("Connecting.....");

        Socket s = ss.accept();
        System.out.println("connected");

        DataOutputStream dos = new DataOutputStream(s.getOutputStream());
        BufferedReader dis1 = new BufferedReader(new InputStreamReader(System.in));

        System.out.println("Enter the path of the File:");
        String path = dis1.readLine();
        FileReader fr = new FileReader(path);
        int ch;

        while ((ch = fr.read()) != -1) {
            dos.writeUTF((char) (ch+3) + "");
        }
        dos.writeUTF("end");

        FileWriter fw = new FileWriter("ServerTXT.txt");
        DataInputStream dis = new DataInputStream(s.getInputStream());
        String data;

        while (!(data = dis.readUTF()).equalsIgnoreCase("end")) {
            fw.write(data);
        }

        fw.close();
        dos.close();
        dis.close();
        s.close();
        ss.close();
    }
}

        FileReader fr = new FileReader(path);

        }
        dos.writeUTF("end");

        fr.close();
        dos.close();
        dis.close();
        s.close();
    }
}
How it works
  • The server reads its file one character at a time, adds 3 to each, and sends every character as its own writeUTF string. The word end is the marker that the file is finished.
  • The client keeps reading strings until it sees end, writing them to ClientTXT.txt. Then it does the same in the other direction: it reads its own file, subtracts 3 from each character, sends them and an end. The server writes them to ServerTXT.txt.
  • +3 going one way and -3 going the other makes the two directions use opposite shifts.

Code: TCPServer.java
java
import java.io.*;
import java.net.*;
import java.util.*;

public class TCPServer {
    public static void main(String args[]) throws Exception {
        if (args.length == 0) {
            System.out.println("Please enter the server directory address as the first argument.");
            return;
        }

        int port = (args.length >= 2) ? Integer.parseInt(args[1]) : 3333;
        String dirName = args[0];

        System.out.println("Server started...");
        System.out.println("Waiting for connections...");

        try (ServerSocket welcomeSocket = new ServerSocket(port)) {
            int id = 1;
            while (true) {
                Socket connectionSocket = welcomeSocket.accept();
                System.out.println("Client with ID " + id + " connected from " +
                        connectionSocket.getInetAddress().getHostName() + "...");
                Thread server = new ThreadedServer(connectionSocket, id, dirName);
                id++;
                server.start();
            }
        }
    }
}

class ThreadedServer extends Thread {
    private Socket connectionSocket;
    private String dirName;

    public ThreadedServer(Socket s, int c, String dir) {
        this.connectionSocket = s;
        this.dirName = dir;
    }

    public void run() {
        try (BufferedReader in = new BufferedReader(new InputStreamReader(connectionSocket.getInputStream()));
                OutputStream output = connectionSocket.getOutputStream();
                PrintWriter out = new PrintWriter(output, true)) {

            File directory = new File(dirName);
            if (!directory.exists() || !directory.isDirectory()) {
                System.out.println("Invalid directory specified.");
                return;
            }

            // Send file list to the client
            String[] fileList = directory.list();
            out.println(fileList.length);
            for (String file : fileList) {
                out.println(file);
            }

            String request = in.readLine();
            if (request == null)
                return;

            if (request.startsWith("*")) { // Download
                String filename = request.substring(1);
                File file = new File(dirName, filename);
                if (file.exists() && file.isFile()) {
                    out.println("Success");
                    try (FileInputStream fileInput = new FileInputStream(file)) {
                        sendBytes(fileInput, output);
                    }
                } else {
                    out.println("FileNotFound");
                }
            } else { // Upload
                String filename = request;
                File file = new File(dirName, filename);
                try (FileOutputStream fileOut = new FileOutputStream(file)) {
                    receiveBytes(in, fileOut);
                }
                out.println("UploadSuccess");
            }
        } catch (IOException ex) {
            System.out.println("Exception: " + ex.getMessage());
        }
    }

    private static void sendBytes(InputStream in, OutputStream out) throws IOException {
        int c;
        while ((c = in.read()) != -1) {
            out.write((c + 3) % 256); // Caesar cipher encryption
        }
        out.flush();
    }

    private static void receiveBytes(BufferedReader in, OutputStream out) throws IOException {
        int c;
        while ((c = in.read()) != -1) {
            out.write((c - 3 + 256) % 256); // Caesar cipher decryption
        }
        out.flush();
    }
}

How it works
  • When a client connects, the server starts a new ThreadedServer thread for it and goes straight back to accept(). That is what lets several clients connect at once.
  • The first thing the server sends is the number of files in its folder, then each file name, one per line.
  • The client then sends one line. A line starting with * means download; the name after the star is the file. Any other line is the name of a file the client is about to upload.
  • Download: the server replies Success (or FileNotFound), then streams the file with each byte encrypted. The client decrypts each byte as it writes the file.
  • Upload: the client sends the file name line and then streams the file with each byte encrypted. The server decrypts each byte and writes the file. The data ends when the client closes the connection.
  • sendBytes and receiveBytes are the whole cipher: one loop that reads a byte, shifts it and writes it.

Aim

To write a Java program in which a client calls a method that actually runs on a server (here, adding two numbers), using Remote Method Invocation.

Theory
  • RMI lets a Java program call a method on an object that lives in another JVM (possibly another machine) as if it were a local call.
  • Remote interface: declares the methods the client may call. It must extend java.rmi.Remote, and every method must declare throws RemoteException.
  • Implementation class: the server-side class that implements the interface. Extending UnicastRemoteObject makes the object exportable so it can receive remote calls.
  • Stub: a proxy object on the client side. The client calls the stub; the stub sends the call over the network (marshalling the arguments) to the server and returns the result.
  • RMI registry: a small name service. The server registers its object under a name (rebind); the client finds it by that name (lookup). It listens on port 1099 by default and is started with rmiregistry.

Aim

To simulate a wired network of six nodes that carries one UDP flow and one TCP flow at the same time, and to measure the packets received, the throughput and the packets dropped from the trace file.

Theory
  • UDP + CBR: UDP is connectionless and gives no delivery guarantee. CBR (constant bit rate) is the traffic generator that sends fixed-size packets at a steady rate. The receiver is an Agent/Null, which simply discards what arrives.
  • TCP + FTP: TCP is reliable and uses congestion control. FTP is the application that keeps sending data as fast as TCP allows. The receiver is a TCPSink, which sends the ACKs.
  • DropTail: a queue that drops the newest packet when it is full.
  • Bottleneck: the slowest link on a path (here n1-n4 at 3 Mb) limits throughput, and the queue before it is where packets get dropped.
  • Throughput = total bits received / time over which they were received.

BEGIN { sent=0; recv=0; dropped=0; bytes=0; first=0; last=0; flag=0 }
{

    if ($1 == "r" && $5 == "tcp" && $4 == 5) {

        last = $2
    }
    if ($1 == "d") dropped++
}

Theory

  • Congestion avoidance: above ssthresh, cwnd grows by about one packet per round trip.
  • On loss, ssthresh is cut and cwnd shrinks. The variants differ in how.

Aim

To simulate Distance Vector and Link State routing on a seven-node ring, fail a link during a TCP transfer, and observe how each protocol reroutes the traffic and recovers.

Theory
  • Distance Vector (DV): each router tells its neighbours its distance to every destination, and updates its own table with the Bellman-Ford rule. It only knows the next hop and cost, not the whole map. Used in RIP. Slower to converge and can suffer count-to-infinity.
  • Link State (LS): each router floods information about its own links to every router, so all routers hold the same map and each runs Dijkstra's shortest path algorithm. Used in OSPF. Converges faster but uses more memory and flooding traffic.
  • NS2 uses static routing by default. rtproto DV or rtproto LS switches on a dynamic routing protocol, which is what lets the network react to a link failure.

  3. Attach a TCP agent to node 0 and a TCPSink to node 3 and connect them. Add FTP on the TCP agent.
  4. Start FTP at 0.5 s. Bring the link between node 2 and node 3 down at 2.0 s and up again at 3.0 s. Stop FTP at 4.9 s and finish at 5.0 s.
  5. record writes the sink's throughput every 0.1 s into dvr_th (or lsr_th).
  6. Run ns DV.tcl, then ns LS.tcl. Compare the two graphs and the nam animations.

Aim

To simulate multicast communication using Dense Mode routing, where two sources each send to a group address and receivers join and leave the groups during the run.

Theory
  • Unicast is one sender to one receiver. Broadcast is one sender to everyone. Multicast is one sender to a chosen group of receivers, and the sender sends each packet only once.
  • Receivers show interest by joining a group, identified by a class D address (224.0.0.0 to 239.255.255.255). Joining and leaving is handled by IGMP in real networks.
  • Dense Mode (DM) assumes most routers have members. It floods the first packets to every branch and then prunes the branches that have no members (flood and prune, as in DVMRP). Sparse Mode (PIM-SM) works the other way: branches are added only when a receiver asks.
Procedure

  2. Create eight nodes and seven 1.5 Mb links.

Aim

To implement a simple DHCP server and client in Java using UDP sockets, where the server assigns an IP address from its address pool to every client that requests one.

Theory
  • DHCP (Dynamic Host Configuration Protocol) gives a host its IP address, subnet mask, gateway and DNS automatically, so nobody configures each machine by hand.
  • The real protocol has four steps, remembered as DORA: the client broadcasts Discover, the server replies with an Offer, the client sends a Request for that offer, and the server sends an Acknowledge. The address is leased for a limited time.
  • Real DHCP runs over UDP, server port 67 and client port 68. UDP is used because the client has no IP address yet and so cannot hold a TCP connection.
  • This program is a simplified version: one request message and one reply message, on port 4900 so it needs no administrator rights.
Procedure
  1. Write DHCPServer.java: fill a list with 192.168.1.2 to 192.168.1.254, open a DatagramSocket on port 4900, and loop forever receiving requests.
  2. For each request, remove the first address from the list and send "Allocated IP: ..." back to the sender's address and port.
  3. Write DHCPClient.java: send "DHCP Request with MAC: 00:11:22:33:44:55" to the server, wait for the reply, and print it.
  4. Compile: javac DHCPServer.java DHCPClient.java.
  5. Terminal 1: java DHCPServer. Terminal 2: java DHCPClient. Run the client again to see the next address.
Code: DHCPServer.java
java
import java.net.*;
import java.util.*;

public class DHCPServer {
    private static List<String> availableIpAddresses = new ArrayList<>();

    public static void main(String[] args) {

        for (int i = 2; i <= 254; i++)
            availableIpAddresses.add("192.168.1." + i);

        try {
            DatagramSocket socket = new DatagramSocket(4900);
            while (true) {
                // Receive
                byte[] receiveData = new byte[1024];
                DatagramPacket receivePacket = new DatagramPacket(receiveData, receiveData.length);
                socket.receive(receivePacket);

                // Extract
                InetAddress clientAddress = receivePacket.getAddress();
                String allocatedIp = availableIpAddresses.remove(0);

                // Response
                byte[] responseData = ("Allocated IP: " + allocatedIp).getBytes();
                DatagramPacket responsePacket = new DatagramPacket(responseData, responseData.length,
                        clientAddress, receivePacket.getPort());
                socket.send(responsePacket);

                // Display
                System.out.println("Allocated IP " + allocatedIp + " to MAC " + "00:11:22:33:44:55");
            }
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
Code: DHCPClient.java
java
import java.net.*;

public class DHCPClient {
    public static void main(String[] args) {
        try (DatagramSocket socket = new DatagramSocket()) {
            // Request to server
            InetAddress serverAddress = InetAddress.getByName("127.0.0.1");
            byte[] requestData = ("DHCP Request with MAC: 00:11:22:33:44:55").getBytes();
            DatagramPacket requestPacket = new DatagramPacket(requestData, requestData.length, serverAddress, 4900);
            socket.send(requestPacket);

            // Receive
            byte[] receiveData = new byte[1024];
            DatagramPacket receivePacket = new DatagramPacket(receiveData, receiveData.length);
            socket.receive(receivePacket);

            // Display
            String response = new String(receivePacket.getData()).trim();
            System.out.println("Received DHCP Response: " + response);

            socket.close();
        } catch (Exception e) {
            e.printStackTrace();
        }
    }
}
Line-by-line explanation
  • List<String> availableIpAddresses is the address pool. The loop from 2 to 254 skips .0 (network), .1 (usually the gateway) and .255 (broadcast).
  • new DatagramSocket(4900) makes the server listen on UDP port 4900. The client uses new DatagramSocket(), which picks any free port.
  • socket.receive(receivePacket) blocks until a datagram arrives. After it returns, getAddress() and getPort() tell the server who sent it.
  • remove(0) takes the first free address out of the pool, so no address is given twice.
  • The reply goes to clientAddress and receivePacket.getPort(), which is how a connectionless UDP server answers.
  • The client calls send then receive. trim() removes the unused zero bytes left in the 1024 byte buffer.
  • 127.0.0.1 means the client and server run on the same machine. To use two machines, put the server's IP address there.
Expected output

Server terminal, one line per client:

text

Allocated IP 192.168.1.3 to MAC 00:11:22:33:44:55

text

The server prints a fixed MAC string; it does not read the MAC out of the request. The client's own request text is what carries it.

Viva questions
  • What does DHCP do? Gives hosts an IP address and network settings automatically.
  • Four DHCP messages? Discover, Offer, Request, Acknowledge (DORA). This program implements only one request and one reply.
  • Why UDP? The client has no IP address yet, and UDP needs no connection. Real DHCP uses ports 67 (server) and 68 (client).
  • Why does the server use a fixed port but the client does not? The client must know where to send; the server can reply to whatever port the request came from.
  • What is a lease? The time the client may keep the address. This program does not implement leases or release.
  • What happens when the pool is empty? remove(0) throws an IndexOutOfBoundsException, caught and printed by the catch block.
Common errors
  • Starting the client before the server: receive blocks forever because nobody answers.
  • java.net.BindException: Address already in use: an old server is still running on port 4900.
  • Compiling only one file, or running from a different folder, gives "Could not find or load main class".
  • Class name must match the file name: DHCPServer in DHCPServer.java.

Aim

To simulate a wired Ethernet LAN (IEEE 802.3, CSMA/CD) with six nodes sharing one medium, run two FTP transfers over it, and calculate throughput from the trace file.

Theory
  • Classic Ethernet is a shared bus: every node sees every frame, and only one node can transmit at a time. All the nodes form one collision domain.
  • CSMA/CD is the access method. Carrier Sense: listen before sending. Multiple Access: many nodes share the wire. Collision Detection: if two nodes send together, they detect the collision, send a jam signal, stop, wait a random time, and try again.
  • The wait uses binary exponential backoff: after the n-th collision the node waits a random number of slot times between 0 and 2^n - 1, so repeated collisions spread the retries further apart.
  • In NS2, make-lan joins a list of nodes with a shared link and adds one extra virtual node to represent the LAN itself.
Procedure
  1. Create the simulator and open LAN.tr and LAN.nam.
  2. Create six nodes n1 to n6.
  3. Join them with make-lan: 0.2 Mb shared bandwidth, 20 ms delay, link layer LL, queue Queue/DropTail, MAC Mac/802_3.
  4. Create two TCP senders on n1 and n2, and two TCPSinks on n5 and n6. Connect each sender to its sink.
  5. Attach an FTP application to each sender. Start the first at 0.1 s and the second at 0.4 s.
  6. Run to 10 s. finish flushes the trace, closes the files, and starts the awk script.
  7. Run ns ethernet_lan.tcl, then gawk -f analysis.awk LAN.tr.

Aim

Theory
  • IEEE 802.11 is Wi-Fi. Wireless nodes cannot detect collisions while sending, so it uses CSMA/CA (collision avoidance) in its DCF mode: listen, wait a random backoff, send, and wait for an ACK.   • AODV (Ad hoc On-demand Distance Vector) finds routes only when needed. A source broadcasts a route request (RREQ); the destination, or a node that knows a route, answers with a route reply (RREP) along the reverse path. Route errors (RERR) report broken links.
  • Radio range is limited (about 250 m by default in NS2), so distant nodes talk through intermediate nodes. That multi-hop behaviour is what AODV handles.
  • TwoRayGround is the radio propagation model: signal strength falls with distance, using the direct and ground-reflected rays.

Optional analysis for the trace (my addition; use it only if the exam asks for delivery ratio or throughput)

awk
BEGIN { sent = 0; recvd = 0; bytes = 0; first = 0; last = 0; flag = 0 }
{
    if ($4 == "AGT" && $7 == "cbr") {
        if ($1 == "s") sent++
        if ($1 == "r") {
            recvd++
            bytes += $8
            if (flag == 0) { first = $2; flag = 1 }
            last = $2
        }
    }
}
END {
    print "Packets sent     :", sent
    print "Packets received :", recvd
    print "Delivery ratio   :", recvd / sent * 100, "%"
    print "Throughput (kbps):", bytes * 8 / (last - first) / 1000
}

Line-by-line explanation
  • The val array is only a set of named settings; node-config uses them. Every wireless script needs the same block.
  • namtrace-all-wireless file 800 800 tells nam the size of the area. Topography with load_flatgrid 800 800 gives the nodes a flat 800 x 800 m field to be placed in.
  • create-god makes the General Operations Director, a global object that holds node and connectivity information for the simulator. It takes the number of nodes.
  • node-config is set before the nodes are created and applies to every node created after it: routing protocol, MAC, queue, antenna, propagation, channel.
  • random-motion 0 stops random movement; the nodes only move when setdest tells them to.
  • setdest x y speed moves a node. At 3000 m/s the move is effectively instant, so this just places the nodes.
  • Agent/LossMonitor is a receiver that counts packets, bytes and losses. Its bytes_ variable is what the long version samples to get throughput.
  • The CBR source sends a 1000 byte packet every 0.015 s, about 533 kbps, for 780 seconds.
  • The 20 s start leaves time for the nodes to settle before AODV discovers the route.

Viva questions
  • CSMA/CD versus CSMA/CA? CD detects a collision while sending and works on wired links. CA avoids collisions with random backoff and ACKs because a wireless node cannot hear while it transmits.
  • What is the hidden terminal problem? Two nodes out of each other's range both send to a node in the middle and collide there. RTS/CTS reduces it.
  • How does AODV work? On demand: broadcast RREQ, RREP returns along the reverse path, RERR on link break.
  • Proactive versus reactive routing? Proactive (DSDV) keeps routes to everyone all the time; reactive (AODV, DSR) finds routes when needed.
  • What is GOD? A global simulator object that holds node and connectivity information.
  • Why does the n0 to n3 flow need multiple hops? The distance is about 360 m, beyond the default radio range of about 250 m.
  • Why LossMonitor and not Null? It counts received packets and bytes, so throughput and loss can be read from it.
Common errors
  • Calling $ns node before node-config: those nodes do not get the wireless settings.
  • Forgetting create-god, or giving it a different node count than val(nn).
  • Using coordinates larger than the 800 x 800 area.
  • A backslash at the end of the last node-config line, which glues the next line onto it.
  • Stopping the run early: the script simulates 900 s of network time, which can take a while on a slow machine, so wait for nam to open.
